# planit keeps its per-ticket sufficiency gate even when project-shaping already produced a good spec

A single `/grilling`-driven project-shaping pass can produce a spec + `CONTEXT.md`/ADRs thorough enough that every ticket in that project goes straight to `/implement` with no per-ticket planning needed — `planit`'s existing sufficiency check (Step 3: if the spec already looks implementation-ready, skip straight to `implementit`) just fires immediately, every time. Observed directly: an ad hoc `grill-with-docs` project-planning session proved sufficient for every ticket in that project without invoking `planit`'s interview at all.

That is not a reason to remove `planit`'s per-ticket gate. Project-shaping happens once, upfront, before any ticket is built. `planit`'s just-in-time pass also reads **merged dependencies as ground truth** — for each already-shipped blocking ticket, the actual merged spec/code, not just the original plan. A project-wide spec frozen at planning time cannot reflect that a later ticket's real dependencies diverged from what was originally envisioned. For small projects, or ones with few real inter-ticket dependencies, that divergence risk is low (which is likely why the ad hoc session above worked cleanly) — but for a larger or more interdependent project, it's real.

Keep `planit` Steps 1–3 (docs-dir resolution, ticket/dependency context gathering, sufficiency check) exactly as they are. Only Step 4's engine changes (`superpowers:brainstorming`/`writing-plans` → `/grilling` + `/domain-modeling`). In practice, given a strong project-shaping pass, `planit` becomes a fast pass-through most of the time — but it stays in place as the safety net for when reality has drifted from the plan.
