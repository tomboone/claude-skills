# implementit falls back to the project-wide spec, and projectit marks tickets loop-ready, so the loop doesn't require a planit pass per ticket

[[0003-planit-keeps-its-per-ticket-gate]] kept `planit`'s per-ticket sufficiency gate as a safety net even when a strong project-shaping pass usually makes it a fast pass-through. In practice this still forced a `planit` run before `implementit` could find *anything* to work from — `implementit` only ever looked for a **per-ticket** plan or spec file (named with the ticket ID), and `/projectit`'s project-wide spec has no ticket ID in its filename, so `implementit` couldn't see it. That defeated the point of a good project-wide spec: the loop still couldn't run end-to-end without a `planit` pass on every ticket first.

Two changes close that gap:

- **`implementit` gets a third fallback.** If no per-ticket plan or spec exists, it fetches the ticket's parent Linear project's description, looks for the `**Project spec:**` line `/projectit` Phase 1 writes, and if present, reads that file and proceeds — instead of stopping and demanding a `planit` run. This fallback **trusts the project spec's coverage of this specific ticket without `planit`'s sufficiency judgment**. That's a deliberate trade, not an oversight: it's what makes an unattended `loop.py` run possible against tickets that never got individual planning, matching how an ad hoc `grill-with-docs` project-planning session worked directly with `/implement` with no per-ticket step at all. `planit` remains available as an opt-in deeper pass for any ticket where this trust turns out to be misplaced (e.g. it built on a since-merged dependency that diverged from plan).
- **`projectit` marks every work ticket `loop-ready` and `repo:<name>` at creation** (Phase 3), reversing the "no labels of any kind" stance from the earlier `projectit`-reduction refactor. That stance existed because, at the time, no ticket had a spec of any kind until `planit` ran — labeling it `loop-ready` would have been a lie. Now that `implementit` can fall back to the project-wide spec, a freshly-created ticket usually *is* loop-ready the moment it exists. The Phase-3 gate still lets the user deselect `loop-ready` per ticket for anything they'd rather plan or review by hand first.

Net effect: `/projectit` → `plugins/personal/scripts/loop.py --waves --merge` can now take a whole project from idea to merged PRs with no required per-ticket planning step, while `/personal:planit` remains the escape hatch for tickets that need it.
